# Decisions (locked)

Settled choices from the grill session. Don't relitigate without an explicit
revisit + a `log.md` note.

**Bar for a new entry — all three must hold:** hard to reverse · surprising
without context · a genuine trade-off with real alternatives. Record the call,
the date, what was rejected, and **why**; the *why* is the load-bearing part,
because a decision without one can only be obeyed or broken, never revisited
intelligently. Everything below carries its rationale in the right-hand column —
keep it that way. Terminology that a decision settles belongs in
[glossary.md](glossary.md), not here.

| D30 | **Per-user accounts replace the shared platform password** (2026-07-08, commit `7caaa42`; revises D2/D28/D29) | The shared `APP_PASSWORD` is gone. Auth is now per-user: **operator-seeded accounts** (no self-registration — `apps/api/scripts/seed.ts`, copied from `seed.example.ts`; passwords **scrypt**-hashed with a per-password salt in `password.ts`), **opaque server-stored sessions** (`sessions` table; login trades username+password for a random 32-byte token via `POST /auth/login`; `/auth/logout` revokes it). | D31 | **Per-user reading progress + exact resume position** (2026-07-08, commit `207cf7b`; revises D9 for position, and the `books.progress` column of D24) | Reading progress + the exact resume position are **per-user**, not global. `reading_progress` table: `(user_id, book_id)` PK → `progress` (0..1, drives the cover bar) + `locator` (opaque resume position: PDF page number string / EPUB CFI) + `updated_at`, both FKs `ON DELETE CASCADE`. `GET /library` merges the caller's progress rows into the shared book list; `PATCH /library/:id/progress` upserts the caller's row (a null `locator` is COALESCE-preserved so a bar-only update can't wipe the saved position). | D33 | **"Reading Room" replaces Quiet Paper as the enforced design system** (2026-08-24; revises D27 and D32's "evolved not pivoted" clause; retires brief 21's grouping UI) | Chosen from three costed directions after a mockup review — see the design study. **Rejected:** *Vault* (near-black, cinematic, artwork-as-palette — strongest for mixed media and the only one that made music a first-class citizen, but a full repaint that also forced the reading themes to be redesigned, ~7–9 briefs); *Index* (dense keyboard-first archive on a command bar — fastest at scale, but cover art all but disappears, and the library isn't yet large enough to need it). Reading Room fixes the same four IA faults for roughly half of Vault's cost while keeping the warm, typographic character the product already had. **What it locks:** (a) **one home, no tabs** — `kind` is a filter chip with a count, not a route, reversing D32/brief 25's promotion of a filter to navigation; (b) **Continue is the hero**, labelled in time remaining; (c) **tint carries kind** — four paper tints replace format badges as the primary kind signal; (d) **playback persists** in a dock that survives navigation (borrowed from the rejected Vault — a genuine capability gap, not paint); (e) **type is Newsreader + Archivo**, retiring Playfair Display, Source Serif 4 and Inter (three self-hosted families → two, a payload reduction); (f) **dark goes warm** (`#141310`, not `#181818`) so cover art doesn't read sour; (g) **Notes stays its own destination**, outside the media grid — a notebook is authored, not collected; (h) **Shelves ⇄ Stacks grouping is removed** (brief 21's UI; its backfilled author/series/subject columns stay populated and feed search + chips instead). The `--reader-*` three-theme architecture and the `--paper`/`--ink`/`--accent` token *identifiers* survive unchanged (D32's no-churn principle). Motion idiom is **Motion Primitives**, with **anime.js** only on the progress rail; **SmoothUI rejected** as a near-total overlap with Motion Primitives. |

| D34 | **Convert is symmetric, library-attached, and produces a readable linked row** (2026-08-24, brief 34; **revises D1 and D15**) | Grilled with the owner over five rounds. **Convert** is now one verb for either direction — PDF→EPUB or EPUB→PDF. A conversion is **its own `books` row** linked to its source by `converted_from`, not an alternate file on the source's row: per-format resume positions and "which format did I last use" then fall out of the existing `reading_progress` rows for free, the reader needs no variant parameter (you just open a different book id), and a third format later is another row rather than another column pair. The cost is one FK plus `WHERE converted_from IS NULL` on three list statements — and since search is client-side over the loaded list, search/grouping/chips/counts inherit the hiding for free, so one book stays one card. **Revises D1** ("EPUB→PDF is export-only, never a reading path"): D1's *reason* — "conversion discards reflow" — is direction-specific and inverts for PDF→EPUB, which *adds* reflow, so a converted book is now read in-app. The stateless `/convert` route, its temp-file machinery, and the web convert client are **retired**; the EPUB reader's Download-as-PDF is reimplemented as convert-then-download, losing no capability. **Revises D15** (60s synchronous, no queue): conversion is an **async job with a 24-hour ceiling** — a last-resort reaper, not a UX guard — cancellable, **one at a time per account** (a refusal, so "no queue" survives), reaped to `failed` on restart rather than auto-resumed (auto-resume turns one bad row into a boot loop). The client polls at a flat 30s **driven by the row's status, not a client-side started-it flag**, which is what makes "start it, refresh, come back hours later" behave identically. **Rejected:** one row with a sibling file (needed a locator column, a last-variant column, and a variant param threaded through the reader); a separate "reflow" term for the new direction (the owner wanted one word); a 10-minute ceiling; tapered polling. **Quality caveat, recorded because it is the reason the source stays reachable:** Calibre's own manual calls PDF *"a really, really bad format to use as input"* with output *"anywhere from decent to unusable"* — multi-column interleaves, headers/footers pollute the body, no OCR. Hence: never auto-convert on upload, always keep the source one tap away, and warn (never block) when the output looks scanned. |
| D35 | **Profiles are an identity boundary inside an account — explicitly not a security one** (2026-08-24, brief 35; **revises D30, D31 and D9**) | Owner's framing: *"an account is like a household, while profiles are for different persons from the household. They can change freely the profile."* So an **account** is the household and keeps being the security boundary (D30's scrypt + opaque sessions, unchanged); a **profile** is a person in it. Free switching — no password, no PIN — means anyone holding a live session can become any profile on that account; **this is the design, not a gap**, and it is recorded because the tempting later mistake is to treat a profile as a permission. Housemates needing real separation need a second *account*. **Revises D31**: reading progress and the resume locator move from user scope to profile scope (a `reading_progress` rebuild — SQLite cannot ALTER a composite PK); **revises D30**'s "only identity and progress are per-user" to add notes and preferences; the library stays shared across profiles as it is across users. **Revises D9** ("display state is device state") for preferences only: theme, font settings, page mode and TOC sidebar move **server-side** into one JSON blob on the profile row, so they follow a person between devices — mirrored to localStorage as a synchronous boot cache, since a server-fetched theme otherwise paints wrong and snaps. Reading *position* stays D31's locator, not a preference. **Why not just more accounts?** D30 already gives multi-account + shared library + per-user progress; the entire delta is friction — one tap versus a password, a button versus `scripts/seed.ts` over SSH — and on a shared tablet that friction is the whole feature. **Rejected:** a per-request profile header (media tags cannot send headers — the codebase already fell back to `?token=`, so it would need a query-param twin); minting a token per profile (logs other tabs out); always showing the picker (a tax on the 90% of loads that are one person on their own phone) and never showing it (a tablet with no session expiry silently attributes everyone's reading to whoever used it last — hence the 24h idle re-prompt, measured device-side). Cap of five profiles; offline blobs stay device-scoped; no kids/content-restriction concept. |

| D36 | **Atrium is a personal cloud space, not a media gallery** (2026-08-24, brief 36; **supersedes D32's framing clause**) | Owner, on why LaTeX belongs here: *"it is in Atrium for the same thing as notes. Maybe you are on the road and want to sync what's on your phone with what's on pc and vice-versa. It's like a personal cloud space."* D32 called the product "a media gallery + Notes". Notes was the first thing that didn't fit "gallery"; LaTeX is the second, and two is a pattern — so the premise is recorded as **your stuff, reachable from anywhere**: media you collect *plus* documents you author. Practical consequences: authored destinations (`/notes`, `/latex`) sit **outside** the media grid and always will (D33's rule generalizes); a third authored thing needs no further premise debate; and PRODUCT.md is rewritten in brief 36 rather than drifting a third time. **Rejected:** a separate app sharing the design system — it would mean re-solving auth, profiles, deploy and design for one user. Everything else in D32 (the name, the kept internal `book`/`library` nouns, the `/atrium/` deploy path) stands. |
| D37 | **LaTeX runs server-side on Tectonic; drafts and published documents are different things** (2026-08-24, brief 36) | Grilled over three rounds. **Engine:** server-side **Tectonic** — a single self-contained binary that downloads packages on demand (~75 MB image) rather than a ~5 GB TeX Live install. Chosen on **precedent and payload**: D5 already accepts a binary dependency for a core capability, and the app's entire initial JS is 123 kB gzip after briefs 15–17 spent their effort trimming it, so shipping a WebAssembly TeX engine to a phone reverses that work. **Rejected: SwiftLaTeX/WASM** — it buys offline compilation nobody asked for (v1 is online-only, matching Notes/D32), costs multiples of the whole 3 MB precached shell on the device least able to afford it, and is AGPL-3.0. **Sandboxing is spec, not afterthought**, because running code is what TeX *is*: shell escape (`\write18`) explicitly disabled rather than trusted to a default, every project path confined to its project directory (no absolutes, no `..`, no symlinks out), a short hard wall-clock timeout (a compile someone is waiting on has no reason to run long — unlike D34's 24h conversion ceiling), and a capped artifact size. **Draft vs published:** a **draft** is the live project, lives only in `/latex`, and is never shown in the gallery. **Publishing** compiles, refuses to publish a failing document, and produces **one** library entry that accumulates **versions** — pressing publish ten times gives ten versions on one card, never ten cards. Each version stores its PDF **and a zip of the whole project**, so a version can actually be rebuilt (figures included); `books.file_path` tracks the newest version so every existing consumer — file route, offline download, reader — works unchanged, with `?version=` selecting an older one. A new version starts at page 0; `reading_progress` gains a nullable `version_id` so a stale locator is never applied to the wrong version (no PK rebuild). Deleting a version removes its files; deleting the library entry removes all versions; deleting the draft leaves the published entry alone — publishing is the act of making something independent. **v1 is deliberately three features** (multi-file projects, compile + preview, diagnostics with file and line); autocomplete, SyncTeX, collaboration, templates, rich-text and bibliography tooling are all out. Editor is **CodeMirror 6**, not Monaco (~10× the entry chunk for one destination, and not touch-credible) — phone support is *light edits*, not authoring. |

## After-conversion UX (D1 detail)
Two buttons only: **Download** (save the PDF) and **Go back** (return to
uploader). No "read in new tab" — to read a converted PDF, the user re-uploads
it (which routes through the normal PDF reading path).
