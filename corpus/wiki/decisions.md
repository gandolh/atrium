without context · a genuine trade-off with real alternatives. Record the call,

| D34 | **Convert is symmetric, library-attached, and produces a readable linked row** (2026-08-24, brief 34; **revises D1 and D15**) | Grilled with the owner over five rounds. **Convert** is now one verb for either direction — PDF→EPUB or EPUB→PDF. A conversion is **its own `books` row** linked to its source by `converted_from`, not an alternate file on the source's row: per-format resume positions and "which format did I last use" then fall out of the existing `reading_progress` rows for free, the reader needs no variant parameter (you just open a different book id), and a third format later is another row rather than another column pair. The cost is one FK plus `WHERE converted_from IS NULL` on three list statements — and since search is client-side over the loaded list, search/grouping/chips/counts inherit the hiding for free, so one book stays one card. **Revises D1** ("EPUB→PDF is export-only, never a reading path"): D1's *reason* — "conversion discards reflow" — is direction-specific and inverts for PDF→EPUB, which *adds* reflow, so a converted book is now read in-app. The stateless `/convert` route, its temp-file machinery, and the web convert client are **retired**; the EPUB reader's Download-as-PDF is reimplemented as convert-then-download, losing no capability. **Revises D15** (60s synchronous, no queue): conversion is an **async job with a 24-hour ceiling** — a last-resort reaper, not a UX guard — cancellable, **one at a time per account** (a refusal, so "no queue" survives), reaped to `failed` on restart rather than auto-resumed (auto-resume turns one bad row into a boot loop). The client polls at a flat 30s **driven by the row's status, not a client-side started-it flag**, which is what makes "start it, refresh, come back hours later" behave identically. **Rejected:** one row with a sibling file (needed a locator column, a last-variant column, and a variant param threaded through the reader); a separate "reflow" term for the new direction (the owner wanted one word); a 10-minute ceiling; tapered polling. **Quality caveat, recorded because it is the reason the source stays reachable:** Calibre's own manual calls PDF *"a really, really bad format to use as input"* with output *"anywhere from decent to unusable"* — multi-column interleaves, headers/footers pollute the body, no OCR. Hence: never auto-convert on upload, always keep the source one tap away, and warn (never block) when the output looks scanned. |
| D35 | **Profiles are an identity boundary inside an account — explicitly not a security one** (2026-08-24, brief 35; **revises D30, D31 and D9**) | Owner's framing: *"an account is like a household, while profiles are for different persons from the household. Free switching — no password, no PIN — means anyone holding a live session can become any profile on that account; **this is the design, not a gap**, and it is recorded because the tempting later mistake is to treat a profile as a permission. Housemates needing real separation need a second *account*. **Revises D31**: reading progress and the resume locator move from user scope to profile scope (a `reading_progress` rebuild — SQLite cannot ALTER a composite PK); **revises D30**'s "only identity and progress are per-user" to add notes and preferences; the library stays shared across profiles as it is across users. **Revises D9** ("display state is device state") for preferences only: theme, font settings, page mode and TOC sidebar move **server-side** into one JSON blob on the profile row, so they follow a person between devices — mirrored to localStorage as a synchronous boot cache, since a server-fetched theme otherwise paints wrong and snaps. | D37 | **~~LaTeX runs server-side on Tectonic~~; drafts and published documents are different things** (2026-08-24, brief 36; **engine clause revised by D38**) | ⚠️ **The engine half of this decision is superseded by D38 (2026-08-26) — Atrium compiles LaTeX with its own TypeScript engine, not Tectonic.** Everything below about drafts, publishing, versions and the editor still stands. The original engine reasoning is kept because it is what D38 had to answer. Grilled over three rounds. **Engine (superseded):** server-side **Tectonic** — a single self-contained binary that downloads packages on demand (~75 MB image) rather than a ~5 GB TeX Live install. Chosen on **precedent and payload**: D5 already accepts a binary dependency for a core capability, and the app's entire initial JS is 123 kB gzip after briefs 15–17 spent their effort trimming it, so shipping a WebAssembly TeX engine to a phone reverses that work. **Rejected: SwiftLaTeX/WASM** — it buys offline compilation nobody asked for (v1 is online-only, matching Notes/D32), costs multiples of the whole 3 MB precached shell on the device least able to afford it, and is AGPL-3.0. **Sandboxing is spec, not afterthought**, because running code is what TeX *is*: shell escape (`\write18`) explicitly disabled rather than trusted to a default, every project path confined to its project directory (no absolutes, no `..`, no symlinks out), a short hard wall-clock timeout (a compile someone is waiting on has no reason to run long — unlike D34's 24h conversion ceiling), and a capped artifact size. **Draft vs published:** a **draft** is the live project, lives only in `/latex`, and is never shown in the gallery. **Publishing** compiles, refuses to publish a failing document, and produces **one** library entry that accumulates **versions** — pressing publish ten times gives ten versions on one card, never ten cards. Each version stores its PDF **and a zip of the whole project**, so a version can actually be rebuilt (figures included); `books.file_path` tracks the newest version so every existing consumer — file route, offline download, reader — works unchanged, with `?version=` selecting an older one. A new version starts at page 0; `reading_progress` gains a nullable `version_id` so a stale locator is never applied to the wrong version (no PK rebuild). Deleting a version removes its files; deleting the library entry removes all versions; deleting the draft leaves the published entry alone — publishing is the act of making something independent. **v1 is deliberately three features** (multi-file projects, compile + preview, diagnostics with file and line); autocomplete, SyncTeX, collaboration, templates, rich-text and bibliography tooling are all out. Editor is **CodeMirror 6**, not Monaco (~10× the entry chunk for one destination, and not touch-credible) — phone support is *light edits*, not authoring. |
| D38 | **Atrium compiles LaTeX with its own TypeScript engine — a LaTeX *subset*, not a TeX reimplementation** (2026-08-26, brief 37; **revises D37's engine clause**) | Owner: *"make our own wasm library for parsing Tex and generating pdf's from it. Let's drop the tectonic or other external library idea at all"*, then *"i would like to not introduce another programming language like rust, maybe you can still use javascript?"* — so Atrium writes its own engine, in TypeScript, and depends on no TeX at all. **The scope line is syntax, not semantics.** LaTeX is not a file format but a program: `\catcode` lets a document redefine what characters *mean* mid-parse, so there is no parser to write, only a macro-expansion machine that must then execute the LaTeX kernel. Measured 2026-08-26: `tex.web` is **25,010 lines** of literate Pascal and the LaTeX kernel is **79 `.dtx` files / 4.81 MB** before `article.cls`. Nobody has finished a from-scratch TeX; **Typst's team looked and designed a new language instead**, which is the decisive precedent. So we accept LaTeX-*shaped* documents and implement the commands ourselves — the same shape as LaTeX.js (MIT, maintained), which parses a documented subset and implements macros in JS rather than in TeX. **This is only defensible because brief 36 decision 4 already says the owner has nothing to import**: the engine must render what the owner writes, not what CTAN can produce. If a legacy `.tex` corpus ever appears, this decision is the first thing to revisit. **Why TypeScript and why WASM became unnecessary:** WASM was only ever needed to run *someone else's C* — SwiftLaTeX and BusyTeX are Emscripten ports of pdfTeX/XeTeX. Writing it ourselves, a TS library runs natively in Node *and* the browser with no toolchain, no `.wasm`, no glue. C was offered and declined: it would mean writing font parsing, PDF emission and math layout from nothing, because the C ecosystem's answer to all three *is TeX*. Rust was declined by the owner (no second language) and would have bought only speed. The JS stack carries the parts that are not the engine — `@unified-latex` (AST), `fontkit` (glyphs, subsetting), `pdfkit` (PDF bytes), `hypher` (hyphenation), `mathjax-full` (math). We write the parser bindings, macro layer, document model, box-and-glue layout, line and page breaking, and the diagnostics. **The engine is a pure function with no I/O**, which *deletes* D37's sandboxing spec rather than implementing it: `\write18` cannot execute because no shell escape is written, and `\input{/etc/passwd}` cannot read anything because there is no filesystem — `\input` resolves against an in-memory file map or it is a diagnostic. What replaces the wall clock is a **deterministic step budget** (reproducible where a timer is not), plus output-size and page-count caps. **The loud-failure contract is the spine:** an unimplemented command produces a diagnostic with file and line saying so — never a silent skip, never a guess. A subset engine that renders quietly-wrong output is worse than no engine, because a dropped `\thanks` is a missing footnote in a *published* document. **Costs accepted:** brief 37 is milestoned work, not a week; the repo gains its **first test suite** (golden layout dumps, not PDF bytes) because a typesetting engine without them is unmaintainable; and math ships as MathJax SVG embedded via our own SVG-path→PDF emitter, with TeX's own mlist atom-class layout deliberately deferred. **Rejected:** Tectonic (D37 — MIT, 10 MB binary, but XeTeX-only and a runtime dependency); MiKTeX (all three engines plus on-demand packages, but a system install with a shared package tree); TeX Live (apt's is 2021; full image 7.04 GB); SwiftLaTeX (its package server `texlive.swiftlatex.com` has **no DNS** and `texlive2` returned **HTTP 522 on 4/4 attempts** on 2026-08-26, so it cannot compile at all without self-hosting an unmaintained 2022 server); BusyTeX (maintained, TeX Live 2026, but ~32 MB WASM + 90–400 MB of data, AGPL-3.0); and Typst (single Apache-2.0 binary, excellent — but it is **not LaTeX**, and the owner asked for LaTeX). |

| D40 | **Video covers are decoded in the browser, not by a server binary** (2026-08-27, brief 42; **narrows brief 23's apparent "no video covers"**) | Video was the only kind with no real cover. Brief 23 reads as *no video covers, ever*, but what the owner actually declined was the **ffmpeg binary dependency** — server-side frame extraction was simply the only route on the table then. So this does not reopen that call; it takes a different route to the same feature. **mp4/webm are accepted formats precisely because the browser plays them** (D12, extended by brief 23), so the uploading browser is already a video decoder: object URL → `<video>` → seek → `drawImage` → `toBlob`. No server binary, so the declined-ffmpeg decision stands. **Capture happens in two places** — at upload (~3 candidate timestamps, keep the highest luminance-variance frame, because one fixed seek lands on a black fade-in or a title card often enough to matter) **and as a backfill on first playback**.
